## Follow-up review on 22 October UTC / 23 October Dubai

A fresh review found a missed Engine authentication issue: creation and reset
accepted passwords beyond bcrypt's 72-byte capacity. A synthetic 77-byte
credential authenticated with both a different suffix and its 72-byte prefix.
Installation, administrator/user creation and resets now enforce 8–72 bytes
without null bytes; sign-in rejects overlength/null-byte inputs. Verification
of existing shorter credentials is preserved. Forms keep the full input and
explain the byte limit instead of silently truncating or counting Unicode
characters differently from the server.

Existing hashes cannot identify passwords that originally exceeded 72 bytes.
Their prefix remains usable until an administrator resets the credential;
input validation does not repair those stored hashes. No real accounts were
inspected or reset. See [authentication operations](../security-operations.md#authentication-and-sessions).

The website artifact verifier also accepted a relaxed first CSP directive
hidden by a later strict duplicate. It now follows browser first-directive
semantics, rejects duplicate directives regardless of case, and requires the
policy before resource elements, with six artifact regression checks.
The generated production policy itself had no duplicate directives.

The final full PHP suite passed **132 checks** after the password fix, including
ASCII/Unicode boundaries, suffix rejection, null bytes, mutation-free rejected
resets and existing short-password compatibility. An overlength CLI install
failed before creating a database. PHP lint, publication checks and Cloud's
interface/runtime contract against the changed working Engine passed; the
Cloud release pin remains unchanged. Additional browser and website results
passed: eight Chromium/WebKit application journeys (including complete
overlength-input submission, Unicode password creation and mutation-free
rejected resets), 13 website React tests, six artifact checks, typecheck,
build and ten-file artifact verification. Browser policy tests and all three
lock audits passed with zero known dependency findings.

Separate Chromium/WebKit website probes completed all 16 demo actions, reached
100% progress and reset to zero, and loaded video plus captions without page
errors or unexpected CSP violations. Direct foreign requests and WebSockets
were blocked. This retains the documented redirect limitation.

Those real-browser accessibility scans also found pre-existing presentation
issues: small muted summary/role text has contrast ratios of 4.04:1 and
4.41:1 (below 4.5:1), the completed action-panel kicker reaches only 3.44:1,
and the completed view has an indistinguishable complementary landmark.
Initial contrast findings were identical with and without CSP in both
browsers; the component/CSS sources were unchanged. These remain an
accessibility follow-up, not a passing full website accessibility audit.
No unrelated restyling was made during this security review.

Fresh isolated installs and lock audits covered the website and both browser
QA trees. Cloud's independent report records a malformed optional dependency
checksum discovered during that check. A new Python venv also proved that a
wrong pip wheel hash is rejected, the pinned bootstrap installs certifi

## Checked scope and remaining runtime risks

All 145 website and six browser-QA locked package entries were checked, including
development/transitive dependencies. All use HTTPS npm-registry URLs and
SHA-512 integrity. React/react-dom 19.2.6 remain unchanged; this is client-side
React DOM with no React Server Components or server renderer. Website npm audit
fell from 12 vulnerable package nodes to zero; production-only and QA audits
also report zero. The exact-window reviewed npm feed contained 79 records and
was matched against package names, rather than treating audit output as a
disclosure-date feed.

The six pinned Python validator packages passed pip-audit with no known
vulnerabilities. The PHP product has no Composer dependency tree. CI action
references are immutable SHAs; an expanded check covered 338 unique production
package/version pairs from the actions' published lockfiles. Older bundled
`form-data` 4.0.0 / CVE-2025-7783 was encountered in artifact/deploy actions
(fixed upstream in 4.0.4); an attacker-controlled multipart/PRNG-observation
path was not established for these workflows. This remains a flagged serious
dependency, not an asserted exploitable application flaw.

`setup-node` does not patch the Actions runner's own Node. The earlier inspected
runner v2.338.0 declares Node 24.21.0. A refreshed upstream check found
[runner v2.338.1](https://github.com/actions/runner/releases/tag/v2.338.1),
published 22 October at 14:14 UTC, with [Node 24.22.1](https://github.com/actions/runner/blob/v2.338.1/src/Misc/externals.sh).
That fixed runner was released within the original advisory window. Its
availability does not establish that these hosted jobs received it; the actual
runner version and patch level still require fresh provider/CI evidence.

Playwright 1.62.1 and axe 4.13.0 have no npm audit findings, but Playwright's
manifest bundles Chromium 151.0.7922.34, Firefox 153.0 and WebKit 26.5. These
are not established patched browsers. Firefox's [20 October advisory](https://www.mozilla.org/en-US/security/advisories/mfsa2026-111/)
includes CVE-2026-113399 / CVE-2026-113470, fixed in Firefox 158.0.1 or ESR
153.5.1. Even Playwright 1.64.1's manifest did not establish full coverage of
the latest browser fixes, so a blanket version bump was avoided. Qualification
now requires a loopback HTTP(S) base URL, blocks direct requests to other
origins, WebSockets and service workers, and tests the policy. Playwright does
not re-intercept redirect hops: this is explicitly not complete egress
protection. It limits exposure on trusted synthetic local pages; it does not
patch browsers or provide OS-level process isolation. Upgrade/requalify bundled browsers when
supported builds include the vendor fixes.

## Recovery and deployment steps

Before any publication, save the Pages API configuration, deployment/environment
branch policies, all needed Git refs and an independently retained verified
`website/dist` with checksums. The observed Pages API reports legacy source
`gh-pages:/`, while the latest successful deployment references `main` at
`417e6e4a292d5d7df156076b13d3a5f072afa521` (31 August). Preserve both refs and
resolve that source-mode discrepancy before changing settings; do not switch
publishing modes or delete `gh-pages` during incident recovery.

Restore source from the protected bundle/mirror into a new directory, restore
the saved work patch if applicable, run locked `npm ci` and `npm run check`
under patched Node, compare artifact hashes, preview locally, and publish only
through the existing release process. Provider-managed github.io DNS incidents
belong to GitHub; do not copy these shared IPs to an unrelated new zone.

For a future custom domain, retain the authoritative provider's zone export
and structured configuration (records, TTLs, proxy flags, nameservers, CAA,
mail records, delegation/DS/DNSSEC state), separately from provider account
recovery credentials. Verify delegated authority and HTTPS after a restore;
historical records are corroboration only. Changing registrars/nameservers,
adding Cloudflare or buying independent storage requires an explicit reviewed
impact/rollback plan and account authorization.

For an actual PHP deployment, update the runtime and restart web/worker
processes, run doctor and readiness, then verify authenticated/private cache
behavior, API/webhook traffic and institutional recovery independently. Local
source checks do not demonstrate these deployment steps.
