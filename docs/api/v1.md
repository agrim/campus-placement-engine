# Read-only public API v1

Status: supported public integration surface

API v1 is an institution-local, sessionless read boundary. It exposes only
governed opportunity and application projections. It has no candidate, person,
student-profile, advising, workflow-command, transition, import, export, or
other write endpoint. The separate Cloud control plane never proxies ordinary
API traffic and never receives API response data.

The normative machine documents are:

- `contracts/openapi.v1.json` for paths, methods, parameters, authentication,
  responses, and status codes;
- `contracts/schemas/api-v1-*.schema.json` for strict Draft 2020-12 producer
  shapes;
- `contracts/examples/api-v1-*.json` and `contracts/fixtures/api-v1-*.json` for
  producer and frozen-consumer compatibility; and
- `contracts/public-integration.v1.json` for the supported `v1` declaration and
  exact public scopes.

## Routes and methods

The only public paths are:

| Path | Required scope |
|---|---|
| `/api/v1` | authenticated service account |
| `/api/v1/opportunities` | `opportunities.read` |
| `/api/v1/opportunities/{public_id}` | `opportunities.read` |
| `/api/v1/applications` | `applications.read` |
| `/api/v1/applications/{public_id}` | `applications.read` |

Every path supports only `GET` and `HEAD`. `HEAD` executes the same
authentication, authorization, rate-limit, lookup, and audit path as `GET`,
returns the same status and representation headers, and emits no body. Item
responses include a stable quoted `ETag`; `If-None-Match` can return `304`.
`POST`, `OPTIONS`, and every other method return fixed JSON `405` on a known
route. Unknown routes return fixed JSON `404` and never redirect to the browser
application.

## Authentication and transport

Send exactly one header of this shape:

```text
Authorization: Bearer <Phase3A-token>
```

The complete token grammar and lifecycle are in `authentication.md`. Query
parameters, cookies, browser sessions, setup capabilities, webhook secrets, and
health/metrics bearer tokens are not API credentials. A missing, malformed,
expired, revoked, disabled, unknown, or API-disabled credential receives the
same `401 invalid_credentials` envelope. A valid token without the exact route
scope receives `403 insufficient_scope`. Authentication, authorization,
keyring, request-audit, rate-limit, or database uncertainty fails closed with
`503 service_unavailable`.

Use HTTPS for every non-loopback deployment. CORS is disabled: the API emits no
access-control headers and `OPTIONS` is not a preflight surface. Responses are
JSON with `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, and an
opaque `X-Request-ID`. They never start a PHP session or emit a session cookie.

## Exact data projections

Opportunity data contains only:

```text
id, cycle_id, organization_id, organization_code, organization_name,
opportunity_key, title, status, created_at, updated_at
```

It excludes slot, room, tracker, active caps, process details, deadlines,
notes, tags, custom fields, legacy IDs, and numeric database IDs.

Application data contains only:

```text
id, participant_id, opportunity_id, status, aggregate_version,
created_at, updated_at
```

It excludes candidate/person/student-profile records, external IDs, names,
contact details, programs, tags, accommodation, custom fields, legacy IDs,
company raw IDs, waitlists, offers, notes, workflow internals, and numeric
database IDs. Every query joins through the current institution; another
institution's public ID is indistinguishable from a missing item.

Privacy classification:

- organization and opportunity identifiers and operational fields are
  institution-owned placement operations data;
- application, participant, and opportunity links plus status/timestamps are
  pseudonymous placement records and remain restricted institutional data; and
- none of these responses is anonymous/public-web data. Consumers must apply
  the institution's access, retention, backup, and incident rules.

## Cursor pagination

Collections accept only these optional parameters:

- `limit`: default `50`, minimum `1`, maximum `100`;
- `updated_after`: an exact seconds-precision RFC 3339 UTC timestamp ending in
  `Z`; and
- `cursor`: the opaque signed continuation returned by the preceding page.

Unknown, duplicate, array-shaped, overlong, or malformed parameters are
rejected. `cursor` and `updated_after` cannot be combined. Clients must not
inspect or construct cursors. They bind their format and key version,
institution public ID, route/resource, normalized filter, snapshot upper bound,
and last `(updated_at, public_id)` tuple. A cursor therefore cannot move between
resources, routes, institutions, filters, or keyrings.

Collection order is stable ascending `(updated_at, public_id)` within the
cursor's captured upper bound. The envelope is:

```json
{
  "data": [],
  "page": { "next_cursor": null, "has_more": false },
  "meta": { "request_id": "req_..." }
}
```

This is not a database snapshot transaction across requests. A record updated
after the captured upper bound can leave the continuation, and an update of a
previously returned record can be observed again in a later synchronization.
Consumers must upsert by public `id`, use `aggregate_version` for application
state ordering, and periodically restart from a stored `updated_after`
checkpoint with an overlap appropriate to their recovery policy. A restore or
lost cursor requires a fresh bounded synchronization; there is no unbounded
export endpoint.

## Errors, limits, and audit

Every JSON error has only `code`, fixed `message`, and `request_id` under the
top-level `error` object. An opaque `incident_id` appears only for an unexpected
server failure. SQL, stack traces, filesystem paths, token/account identity,
and raw request values never appear.

| Status | Meaning |
|---|---|
| `400` | invalid query, cursor, timestamp, body, or request shape |
| `401` | indistinguishable invalid credentials |
| `403` | exact scope or enabled Placement policy is absent |
| `404` | unknown route or institution-bound item not found |
| `405` | method other than GET/HEAD on a known route |
| `414` / `431` | request target/query or headers exceed fixed bounds |
| `429` | atomic institution, token, or direct-peer source limit; honor `Retry-After` |
| `500` | opaque unexpected server failure |
| `503` | authentication, authorization, key, audit, rate-limit, migration, or storage state unavailable |

Before authentication, one fixed API-wide gate applies the default 60-second
ceilings of 1,200 requests per institution and 300 per direct peer. After
authentication, route-class gates additionally apply 1,200 per institution,
600 per token, and 300 per direct peer. Forwarded-address headers are not trusted
as source identity. The first over-limit pre-authentication request writes one
aggregate threshold audit in the same transaction that marks the bucket
sentinel; an audit failure rolls both back and returns `503` until they can
succeed together. Later over-limit requests in that bucket are denied without
creating a row per request. Audit stores only fixed route/scope/outcome/
status/detail classes, linked service-account/token keys, request ID, and a
keyed source fingerprint. It stores no raw IP, path, query, header, user agent,
body, credential, or response record. Audit failure denies the request.

## Deployment and parity

`php placement serve` uses `public/router.php`, preserving real static files and
routing clean paths to `public/index.php`. The equivalent direct command is:

```bash
php -S 127.0.0.1:8000 -t public public/router.php
```

Apache uses `public/.htaccess`. Nginx must retain
`try_files $uri /index.php?$query_string;` as shown in
`examples/deployment/nginx-server.conf`. Keep `public/` as the document root;
do not expose `data/`, contracts as runtime secrets, or repository internals.

Self-hosted and managed Engine instances run the same routes, schemas, token
rules, institution joins, and rate/audit boundary. Managed hosting resolves the
tenant before API authentication and does not start or bind a browser session.
Cloud may observe aggregate health only; it must not proxy, cache, inspect, or
store API traffic or institution placement data.

## Versioning

Paths carry the major compatibility version. The v1 producer emits exactly the
declared fields; removing, renaming, changing meaning/type, weakening privacy,
or changing pagination/auth semantics incompatibly requires a new API version.
Consumers should use the frozen v1 fields and tolerate a future explicitly
optional addition, but the strict v1 producer schemas reject undeclared output
today. Command/write APIs and candidate endpoints require separate governance
and are not implied by the v1 read declaration.
